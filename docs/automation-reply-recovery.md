# Durable automatic replies

New SaaS keyword, survey and system replies are saved in `AutomationReplyOutbox` in the same transaction as the inbound message and survey transition. The signed inbound webhook keeps its HTTP 200/TwiML acknowledgement contract, then queues the saved rows through the configured SaaS RQ queue. Redis failure does not discard the response intent or roll back an already committed inbound action. Legacy mode retains its existing synchronous behavior.

Migration 024 only creates the new table and indexes. It does not scan, recreate, send or enqueue historical inbox replies. Retained inbound SID and immutable response body/phone/digest/source/ordinal identify the new intent, including after optional inbox history deletion. Provider attempts reuse the exact existing `automation:<inbound-id>:<ordinal>:<source>:<source-id>` key. Duplicate inbound SIDs resume only those saved rows; they cannot advance a survey, increment a keyword match again, or manufacture a new send key.

`deliver_automation_job(organization_id, outbox_id)` is the RQ entry point. It claims an expiring worker lease and drains an ordered conversation sequence. A later response cannot overtake an earlier pending response, and dependent survey follow-ups stop when an earlier response was not accepted. Intro/question delay is retained as a minimum delay after the preceding response. The worker sleeps only for a short bounded ready delay; longer waits remain saved for the timer.

SaaS inbound changes and actual automatic submissions share the conversation's row lock. The sender reacquires that lock after committing the durable attempt claim, then rechecks the saved outbox identity, expiry, exact survey state, current opt-out/suppression, provider identity and readiness immediately before provider HTTP. A STOP arriving during an in-flight automatic submission waits for that bounded request; after STOP is acknowledged, remaining unsubmitted automatic replies are blocked. Twilio's own opt-out confirmation remains separate; the app does not bypass STOP to send a confirmation.

Known provider acceptance is replayed before current readiness checks solely to finalize history. It never submits the message again. One inbox bubble, the terminal outbox result and its usage-candidate ledger row commit together. If any of those writes fails, they roll back together, while the separately committed provider attempt remains available for deterministic recovery. Provider acceptance without a delivery receipt is labelled accepted/awaiting receipt, rather than claiming carrier or recipient delivery.

Timeouts, connection loss and unknown provider acceptance stay `ambiguous`/`sending` and do not reset to queued. A late local resolution of that exact attempt can complete the same bubble without another provider call. Only a verified Twilio HTTP 429 rejection can retry automatically, using the same attempt key, bounded backoff and `AUTOMATION_REPLY_MAX_RETRIES` (default three retries after the first call). Twilio documents that a 429 request was not processed and is [safe to retry after backing off](https://www.twilio.com/docs/api/errors/20429). Other provider uncertainty is not treated as proof of rejection.

`AUTOMATION_REPLY_MAX_AGE_MINUTES` defaults to 30. New unsubmitted responses outside that window expire explicitly; they do not silently become sent or delivered. Failures/expiry cancel only the exact still-active survey session linked to the new response, leaving newer sessions intact. An incoming answer while its question is still unsubmitted is kept in the inbox without advancing the survey. Unknown accepted-or-not outcomes remain identified as uncertainty, never as proof that no message was sent.

The existing SaaS scheduler oneshot calls `recover_automation_replies()` alongside ordinary user-request recovery. It only examines the new table, resumes due saved queue work, and finalizes locally known outcomes without constructing a provider. Deterministic RQ IDs, worker/enqueue leases and durable provider keys tolerate lost queue acknowledgements and duplicate workers. `AUTOMATION_REPLY_LEASE_SECONDS` defaults to 120; message submission has its separate bounded HTTP timeout. No long-lived request-handler thread is introduced.

Verification covers interruption after inbound commit/before enqueue, between survey replies, after provider commit/before history, and during history/usage persistence; duplicate SID and Redis jobs; STOP at the claim gap and an actual PostgreSQL in-flight lock barrier; uncertainty and bounded 429 retries; history deletion with retained dedupe; paused inbound; question sequencing/delay; migration replay with zero historical backfill; and organization isolation. Independent subprocess tests use real owned PostgreSQL, Redis and RQ to terminate the web/worker processes at the critical boundaries and recover the same SID with one provider submission total. All provider interactions in tests are in-memory mocks protected by a non-local socket guard.
